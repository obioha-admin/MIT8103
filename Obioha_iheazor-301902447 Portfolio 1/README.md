## 1. Case Study Overview

ConnectSphere is a simulated social media platform designed to allow users to create posts, comment on posts, like content, follow other users, and receive notifications.

I selected this case study because social media applications involve different types of relationships between users and their activities. I wanted to understand how these relationships can be properly represented in a relational database.

The system is designed for registered users who can create content and interact with other users.

The main information stored in the database includes user profiles, posts, comments, likes, follower relationships, and notifications.

The aim of this portfolio was to design a database that stores this information in an organised way while maintaining data integrity.

## 2. Database Design

I designed and implemented seven relational tables using PostgreSQL.

| Table | Description |
|---|---|
| `users` | Stores user profiles and authentication-related information |
| `posts` | Stores content created by registered users |
| `comments` | Stores comments and nested replies |
| `post_likes` | Records users who like posts |
| `comment_likes` | Records users who like comments |
| `follows` | Records relationships between followers and followed users |
| `notifications` | Stores notifications generated by user interactions |

Each table was created to handle a specific type of information rather than storing everything in one large table.

This helped me organise the data and reduce unnecessary duplication.

### 2.1 Entity Relationships

The database includes the following relationships:

- One user can create many posts.
- One user can create many comments.
- One post can have many comments.
- One comment can have multiple replies.
- One user can like multiple posts.
- One user can like multiple comments.
- One user can follow multiple other users.
- One user can receive multiple notifications.
- Notifications can reference the user who performed an action and the related post or comment.

The Entity-Relationship diagram illustrates these relationships and shows how the tables are connected through primary and foreign keys.

### 2.2 Nested Comments

One interesting part of the design was implementing nested comments.

I wanted users to be able to reply directly to comments, just as they do on social media platforms.

To achieve this, I used a `parent_comment_id` field that references another comment.

I also added a composite foreign-key constraint to help ensure that a reply belongs to the same post as its parent comment.

This helped me understand how a relational database can represent hierarchical relationships.

## 3. Keys and Constraints

I used primary keys, foreign keys, unique constraints, and check constraints to maintain data integrity.

### 3.1 Primary Keys

Primary keys uniquely identify each record.

For example, the `users`, `posts`, `comments`, and `notifications` tables use their own identity-based primary keys.

This ensures that every record can be uniquely identified.

### 3.2 Foreign Keys

Foreign keys connect related tables and help prevent invalid references.

For example, a post must reference an existing user, and a comment must reference an existing post and user.

During verification, I confirmed that the database contained **15 foreign-key constraints**.

This showed that the relationships were successfully created in PostgreSQL.

### 3.3 Composite Primary Keys

I used composite primary keys in the following tables:

- `post_likes` — `(user_id, post_id)`
- `comment_likes` — `(user_id, comment_id)`
- `follows` — `(follower_id, following_id)`

These keys help prevent duplicate relationships.

For example, the same user cannot create two identical like records for the same post.

### 3.4 Check and Unique Constraints

I added constraints to enforce selected business rules.

These included:

- Preventing empty post content.
- Restricting post visibility to supported values.
- Preventing users from following themselves.
- Restricting notification types to valid values.
- Preventing duplicate usernames and email addresses.

These constraints help protect the database even if an application sends invalid information.

## 4. Database Normalisation

I designed the relational schema to satisfy the principles of Third Normal Form (3NF).

### First Normal Form (1NF)

Each table contains identifiable records, and the design avoids repeating groups.

For example, user posts are stored in the `posts` table rather than storing multiple posts inside one user record.

### Second Normal Form (2NF)

The design ensures that non-key attributes depend on the complete key rather than only part of a composite key.

The junction tables use composite primary keys to represent relationships without unnecessarily duplicating other attributes.

### Third Normal Form (3NF)

I separated information into related tables to reduce duplication and avoid unnecessary dependencies.

For example, user profile details are stored in the `users` table rather than being repeated in every post or comment.

Posts and comments reference their authors using foreign keys.

This makes the database easier to maintain because updating a user's profile does not require updating every post or comment created by that user.

A more detailed explanation is provided in `NORMALIZATION.md`.

## 7. Design Limitations

Although the database includes several integrity constraints, there are still areas that could be improved.

One limitation is nested comments.

The database can ensure that a reply references a comment belonging to the same post, but the current constraints do not completely prevent indirect circular reply relationships.

Another limitation involves notifications.

The database validates selected notification rules, but additional logic would be required to ensure that every notification corresponds to a genuine user interaction.

For a production application, I would also consider additional indexing, security controls, database backups, and monitoring.

These improvements would help make the database more reliable as the application grows.

One of the important things I learned was how to organise a database into different tables based on the type of information being stored.

Adding the composite foreign-key constraint helped me understand how database rules can be used to protect relationships.

I also learned more about composite primary keys while implementing likes and follows.

For example, using `(user_id, post_id)` as a primary key prevents the same user from liking the same post more than once.

One thing that stood out to me was the importance of testing database constraints.

I realised that successfully creating a table does not automatically mean the database design is correct.

By testing invalid relationships and checking the constraints, I was able to understand how PostgreSQL protects the data from incorrect operations.

As a software developer, I can apply what I learned when building applications that involve users, transactions, and complex relationships.

I now understand why it is important to design the database properly before connecting it to the frontend or backend of an application.

Overall, this portfolio improved my understanding of relational database modelling, normalisation, and data integrity.

It also gave me more confidence in designing databases that are organised, maintainable, and suitable for real application development.
