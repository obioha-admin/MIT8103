## 1. Case Study Overview

ConnectSphere is a simulated social media platform designed to support user interactions through posts, comments, likes, follows, and notifications.

The database is used by registered users who create content, interact with other users, and receive notifications. Database administrators manage the underlying database structure, constraints, and performance.

The major data stored includes user profiles, posts, nested comments, post likes, comment likes, follower relationships, and notifications.

## 2. Database Design

The database consists of seven relational tables:

| Table | Description |
|---|---|
| users | Stores user profiles and authentication-related information |
| posts | Stores content created by users |
| comments | Stores comments and nested replies |
| post_likes | Records likes on posts |
| comment_likes | Records likes on comments |
| follows | Records follower relationships |
| notifications | Records notifications generated by user interactions |

### Entity Relationships

- One user can create many posts.
- One user can create many comments.
- One post can contain many comments.
- A comment can have multiple replies.
- Users can like multiple posts and comments.
- Users can follow other users.
- Notifications reference their recipients, actors, and relevant content.

The Entity-Relationship diagram is available in `diagrams/connectsphere_er_diagram.png`.

## 3. Keys and Constraints

The database uses primary keys to uniquely identify records and foreign keys to maintain relationships.

Composite primary keys are used in the `post_likes`, `comment_likes`, and `follows` junction tables to prevent duplicate relationships.

Check constraints enforce selected business rules, including non-empty post content, valid post visibility, valid notification types, and prevention of self-follow relationships.

The schema contains 15 foreign-key constraints, verified through PostgreSQL system catalog queries.

## 4. Database Normalisation

The relational design aims to satisfy Third Normal Form (3NF).

First Normal Form is supported by uniquely identifiable rows and the absence of repeating groups.

Second Normal Form is supported by ensuring that non-key attributes depend on complete candidate keys.

Third Normal Form is supported by separating user information, posts, comments, likes, and follower relationships into related tables rather than duplicating their attributes.

See `NORMALIZATION.md` for the detailed analysis.

## 5. Implementation

The database was implemented using PostgreSQL 18 and pgAdmin 4.

The SQL scripts in the `sql/` directory create the relational tables and apply additional integrity constraints.

Scripts must be executed in dependency order, beginning with `users`, followed by the tables that reference it.

## 6. Testing and Verification

The implementation was checked using PostgreSQL queries and constraint tests.

Verification activities included:

- Inspecting table columns and constraints.
- Confirming foreign-key relationships.
- Inserting and retrieving related user, post, and comment records.
- Testing rejection of self-follow relationships.
- Testing rejection of invalid notification types.

CSV outputs and screenshots are stored in the `evidence/` directory.

## 7. Design Limitations

The database enforces many integrity rules directly through SQL constraints. However, additional logic would be required to prevent indirect cycles in nested comment relationships and to validate that every notification corresponds to a genuine interaction.

These limitations provide opportunities for future database improvements.
